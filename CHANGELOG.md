# Changelog

## Unreleased

- **`card`, `query`, `ready` and children rows show the current spec title.** An item with a spec prints the title of its newest `item.spec` (the same version `spec show` prints), escaped like the card's other inline fields. An item with no spec, or whose newest spec has a missing or non-string title, prints the `item.created` title and still exits 0. `v_items.title` stays the created title. `card --full` names each child's newest `item.spec` event in `source_event_ids`.

## 0.6.1 — 2026-11-21

Two reserved review records, `review.merge-intent` and `review.merge-done`, carry a merge write-ahead on a pull request's linked item without a work loop. The upgrade page now names two 0.6.0 changes an upgrader can hit, the subinterpreter refusal and the shared search-index lock file, and the release checklist now creates one GitHub Release per tag. No new verb, flag or hook, and no migration.

- **Two reserved review records carry merge write-ahead without a work loop: `review.merge-intent` and `review.merge-done`.** The in-process receipt writer records intent and done on the pull request's linked item in one transaction per state change. The closed `{key, pr, head}` payload binds the merge key to a full pull request URL and a 40-hex lowercase head; mismatches and unknown keys are refused without writing. Retrying returns the existing event, an intent after done reports finished, and done without intent refuses `merge_intent_missing`. Generic CLI and library writers and other internal writers refuse both kinds with `reserved-kind:<kind>`; restore requires `--accept-loop-events` and a verified stream digest. Loop management and the loop writer are unchanged.
- **`docs/upgrading.md` 1.8 names two 0.6.0 changes an upgrader can hit.** Section 1.8 now lists the refusal of a ledger open in a subinterpreter (`db_fd_unattributable`, accepted before on Python 3.12 and later) and the shared `.search.db.lock` file with the `search index cleanup skipped PATH: REASON` stderr line and the known limit for a mixed-version upgrade (a refresh can remove a temp a pre-0.6.0 writer is still building), each with what to do. Docs only; the v0.6.0 tag is unchanged.
- **`docs/releasing.md` says to create one GitHub Release per tag.** Section 3 told the releaser to push the tag only and not to create a Release, which contradicts the release standard (one Release per tag, titled with the tag, notes from that version's changelog section, the newest stable version marked Latest). It now ends with `gh release create vX.Y.Z --verify-tag --title vX.Y.Z --notes-file <notes-file>` after the annotated tag is pushed, and shows how to copy the version's changelog section into the notes file. Docs only; no code, test or schema change.

Upgrade with `@v0.6.1`.

## 0.6.0 — 2026-11-21

`search` finds rulings on their own: a `decided:` note, a recorded decision, an item's current spec and a stop point are each a document, and a dotted word is matched as a phrase. Text search output caps each title at 100 characters and says when more matches sit past the limit. `card` keeps `decided:` notes when a busy item is over budget and lists them under Decisions as notes, never as elections. Search recall is now audited as part of normal work: a golden-query suite runs in CI, `search-miss` logs a miss as it happens, and `search-audit` replays the log. `search --mentions ID` finds the rulings on other items that name an item, and an item hit says where it is mentioned. A ledger open inside an exit handler is accepted whatever order the handlers were registered in, and a ledger open in a subinterpreter is refused. `backup --to` refuses a destination whose temp name exceeds the file name limit instead of printing a traceback. Two reserved event kinds, `review.receipt` and `review.grant-cite`, record review rounds, `ledger.verbs.grants.standing` is the gate's read of a grant, and a leftover search-index temp from a rebuild that did not finish is removed on the next refresh when no writer is running.

- **`card` renders each `decided:` note only under Decisions.** The note no longer also appears under Notes, so it counts once against the Markdown card's word budget and a long ruling that fits is not trimmed prematurely. Ordinary notes still render under Notes, including on `--full` cards. JSON keeps the existing `notes` and `decisions` field shapes; trimming still drops links, then ordinary notes, then decided notes.
- **`card` reports a cut `decided:` note under Decisions, not Notes.** When a card trims and drops a `decided:` note, the `(+K cut; ...)` marker now ends the Decisions section, and the Truncated line (and `truncated` and `cuts` in JSON) names `decisions`; before, the cut was counted against Notes, which left Decisions reading `(none)` with no hint that a ruling was cut. A cut ordinary note keeps its marker under Notes, so a card that cut both shows one marker under each heading. Which rows are cut and the trimming order are unchanged, and the JSON field shapes are too.
- **`search` text output caps titles and says when more matches sit past the limit.** Each title prints at most 100 characters, ending with an ellipsis when longer; the score, type, id and 16-token snippet stay. When `--limit` (default 10) cuts the result, the last line is `+more (raise --limit or narrow with --type/--item)`. The search only fetches one extra row, so how many matches sit past the limit is unknown, and the line does not invent a count. `--json` is unchanged: `truncated` is true when more matches exist, and each card's `title` is the stored title (`cards`, `filters`, `limit`, `query`, `ranker`, `refreshed`, `truncated`).
- **`search` indexes rulings as their own documents; a dotted word is a phrase.** An `item.note` whose text, after leading whitespace, starts with exactly `decided:` (the form the agent contract tells a session to write) is now also a `decision` document of its own, titled by its first 80 characters and carrying its item's id; the note stays in its item's document too. Before, it was searchable only as one note among all of its item's notes, under the item's title, so a ruling written on a busy item ranked past the default ten cards. `Decided:`, `decided :` or a note that only contains the word elsewhere is not a decision. `decision.recorded` events (title: the effect; text: the verbatim words, who, and the tag ids) are `decision` documents too, each item's current spec (its newest `item.spec`: the title, body and acceptance) is a `spec` document, and each `item.stopped` point is a `stop` document; `--type` takes `spec` and `stop`, and `--item` keeps them with the item's other documents. An event without the text field is left out of the new document types and indexed as before. A query word holding a dot between two word characters (`release.notes`) is matched as a phrase of its parts, as a hyphenated word already is; a sentence's final dot still splits. The index format is now 4: an index built by an earlier version reads `stale` and the next `search`, `index` or `doctor` rebuilds it. No schema or migration change.
- **Gates decide a grant through `ledger.verbs.grants.standing(lg, grant_id)`.** It returns the grant only when that exact id is `STANDING`, and otherwise raises the refusal `ledger grants --check` exits with (`grant_unknown`, `grant_withdrawn` or `grant_unverified`, exit 3, with the same message); it never returns a grant that is not standing. The id is compared as an exact string: another letter case, a trailing space, a shorter or longer id, a non-string or an id without a `grant:`, `countersign:` or `rung:` prefix is `grant_unknown`. `ledger grants --check` now runs through it, so the two cannot disagree. Reading grants inside an open write transaction no longer fails: `read_grants` (and so `standing`) reads inside the caller's transaction and leaves it open with its pending writes, where before it began its own transaction, which raised, and rolled back in any case. The docstring and `docs/cli.md` no longer say no gate reads the grants; they name the readers it is for (the merge command, the review-run round check, apply-reviewed-patch and design dispatch); each moves to it in its own change. No schema or migration change.
- **Two reserved event kinds record review rounds: `review.receipt` and `review.grant-cite`.** Only the in-process writer in `ledger/receipts.py` writes them; `ledger append`, `append-many`, the library's `append` and `append_many` and every other internal writer refuse them with `reserved-kind:<kind>` (exit 3), and `review.recorded` stays an ordinary kind. `write_receipt` takes the receipt fields and the receipt document's bytes (a UTF-8 JSON object of at most 64 KiB, else `receipt_doc_not_json` or `receipt_doc_too_large`) and, in one transaction, requires the item to be the one item whose `pr` link names the pull request (`pr_item`: `pr_item_missing`, `pr_item_ambiguous`, `receipt_item_mismatch`), attaches the document inline as a `review-receipt` document (an identical inline one already on the item is reused; one stored by path is refused `doc_not_inline`, since its file can go missing), takes `doc_sha256` from the digest the ledger computed (never from the caller), and checks that `prior_receipt`, each `carried_from` and `supersedes` name receipts of that item (`receipt_prior_mismatch`, `receipt_carried_mismatch`, `receipt_supersedes_required`, `receipt_supersedes_mismatch`); any refusal leaves neither event, and an exact retry writes nothing. The payload is closed: a lowercase `owner/repo`, 40-hex `head` and `base`, one of four verdicts, findings of `block`, `harden` or `nit` (at most 200), `open_bugs` equal to the block findings on an `approved` or `changes_requested` receipt and absent on an `unparseable` or `crashed` one, an optional closed `imported_from`, and no `diff` or `row` key; a credential shape in the document or the event refuses it. `write_grant_cite` records that `grant:review-round-past-cap` was standing, with the election that decided it, and otherwise raises `standing()`'s refusal; a cite grants nothing by itself. `restore` refuses an export holding either kind unless `--accept-loop-events` is given (the flag's help names them), `replay_events` refuses them, and the restore drill passes them. Both kinds are durable. No migration or schema version change; an older copy of the ledger does not know the kinds: measured with v0.5.0 on a database holding one receipt, its `verify` refuses `unknown-kind:review.receipt` (exit 3), while its `export` and `card` still exit 0.
- **A golden-query recall suite runs in CI.** `ledger/tests/test_search_golden.py` builds a synthetic ledger and checks (query, expected document, max rank) cases: a case passes only when its document ranks at or above its max rank, with the case's own `--type` filter when it has one, and a case whose document is absent from the results fails instead of being passed over. The first case is a miss found by accident: a ruling written as a `decided:` note on a busy parent item (40 notes) ranked past the default ten cards for the words that named it; the case requires it in the top ten and `--type decision` to isolate it. Further cases cover a dotted word and a hyphenated word. No change to ranking or to the index.
- **`ledger search-miss --query Q --expected EVENT_OR_ITEM [--note T]` logs a miss.** It appends one line to the database's own misses file, `<database file name>.search-misses.jsonl` beside it (`home.db.search-misses.jsonl` for `home.db`, so two databases in one folder never share a log), and does nothing else: no event, no index change, and a refusal writes nothing. `--expected` is `event:N` or an item id; anything else is a usage error that names the form (`expected-bad-form`, `query-empty`, `repeated-option` and the rest, listed in `docs/cli.md`). The append is one `write` on an `O_APPEND` descriptor, so concurrent writers each add a whole line; a symlink or a file that is not a regular file is never written through, and a write that fails once the file is open (a size or quota limit, a full disk, an I/O error, a failed close) is refused as `misses-file-write-failed` (exit 3, with the JSON envelope), never an uncaught error.
- **`ledger search-audit` replays the logged misses and prints the rank each gets now.** It reads only its own database's misses file. A miss that ranks past ten, or not at all, is listed as a candidate golden case, with the case as JSON under `--json`. It only reads: it never refreshes the index, so an index that is not current, a misses file that cannot be read and a line off the file's grammar are each unverifiable (exit 3, code `unverifiable`, no rank printed), and the message names the line and the form. `search()` gains `refresh=False` for this, which raises `IndexNotCurrent` instead of rebuilding; the default is unchanged. No schema or migration change.

- **`search --mentions ID` lists the documents on other items that name an item, and an item hit prints where it is mentioned.** A ruling about an item often sits on another item (its parent, a readout, an initiative) and names the item's id in its text; finding it took the trick of searching the bare id. `ledger search --mentions ID` now prints the `decision`, `spec`, `stop` and `utterance` documents of other items whose title or content holds ID as a whole token, compared exactly as the id is stored (`child-item` is in `see child-item.` but not in `child-item-2`, `xchild-item`, `child_item` or `Child-Item`; an index match that fails the whole-token check is dropped), decision documents first with a `decided:` note ahead of any other decision, then the rest in rank order. A `decided:` note here is an `item.note` event; a `decision.recorded` whose effect and verbatim words both start with `decided:` is an ordinary decision and ranks with the other recorded decisions, so two of them never take the note's place in the first lines. It takes `--limit`, `--type` and the other search filters and prints the normal text and `--json` shapes (`query` is the id, `filters` carries it as `mentions`). An id that names no item in the ledger is a usage error that names it (exit 2), never an empty result; a known item nothing mentions exits 1. An item never mentions itself, and an `item` document is not a mention: it folds all of its item's notes and names no single event, so a plain note that names an item, and is not a `decided:` note, is not found this way. In text output an `item` hit is followed by up to two lines `mentioned in: ITEM event=N TEXT` (TEXT is the first 80 characters of the document's title), `decided:` notes first, and none when nothing mentions it. Only text output changes: the hits, their order and `--json` are as before. `search` takes `WORD` or `--mentions ID`, not both; with neither it is a usage error. `ledger.search` gains `mentions()`, `item_mentions()` and `names_item()`. A golden case and tests cover it. No index format, schema or migration change.

- **A leftover search-index temp from a rebuild that did not finish is removed on the next refresh, but only when no writer is running and only when it is positively identified as one.** `index`, `index --rebuild`, `search` and `doctor` write the new index in a `.search.db.<id>.partial` file beside `search.db`. Every writer now holds a shared lock on one lock file beside the index, `.search.db.lock` (created empty with mode 0600 when absent, opened without following a symlink, never removed or replaced), from before it creates its temp until that temp is published or removed. After its own publish, and after it has released its shared lock, a refresh asks for an exclusive lock on that file without waiting. Only when it gets it, so no writer is running, does it look at each file whose name matches `.search.db.<id>.partial` exactly, and it removes one only when it is a regular file with no SQLite `-journal`, `-wal` or `-shm` file beside it that is either empty or a SQLite file (its first 16 bytes are the SQLite header) whose tables, read through a read-only immutable connection that creates no side file, are all tables the index writer itself creates (an index or trigger on one of them is allowed), and only when its device, inode and size are unchanged just before the unlink. Anything else whose name matches, such as a ledger backup made with `ledger backup --to .search.db.snapshot.partial`, another ledger, any file holding an `events` table or a view, a symlink, a directory, a short or non-SQLite file, or one that cannot be read, is left byte for byte as it was, and each refresh prints one `search index cleanup skipped PATH: REASON` line on stderr for it; the refresh still succeeds. A held lock, a lock file that is a symlink, is not a regular file or cannot be opened, a platform without `fcntl`, a name that only contains the pattern, or a leftover of another file leaves every file in place and prints nothing. A removal error is one line on stderr and does not fail the refresh or lose the new index. The ledger database and the lock file are never removed: a candidate that is the ledger database's own file (same device and inode, so a hard link under another name too) or whose name begins with the database's file name is skipped, even when the `--db` file is itself named like a partial, and a candidate that cannot be compared with the database is left in place. A killed rebuild whose temp has a `-journal` beside it is reported, not removed. Two overlapping rebuilds both publish, and the index keeps mode 0600. A writer from a version before this change takes no lock, so a refresh that runs while such a writer is mid-build during an upgrade can remove that writer's temp; that writer's refresh then fails, and the next refresh rebuilds. No schema or migration change.
- **`backup --to` refuses a destination whose temp name exceeds the file name limit.** The temp is `.ledger-backup.FILE.<random>.partial` beside FILE. When `mkstemp` fails with `ENAMETOOLONG`, that is a `LedgerError` (exit 3, one stderr line naming the file name limit): nothing is written in the destination directory. A name the destination file system accepts still backs up, including a multibyte name that is within that file system's own limit. Length is not computed by the ledger, so a character-limited volume is not refused on encoded byte length. The destination name is not truncated. Only `ENAMETOOLONG` from the temp creation is converted; any other `OSError` from `mkstemp` still propagates. No schema or migration change.

- **`backup` writes its copy at `.ledger-backup.FILE.<random>.partial`, a name the search-index cleanup never matches.** Before, the copy was written at `.FILE.<random>.partial`, so a backup to a destination named `search.db` or `search.db.<anything>` made a temp that matched the `.search.db.<id>.partial` name pattern the search-index refresh cleans up, and a refresh running at the same time could remove the temp and make the backup refuse. The fixed `.ledger-backup.` start means no destination name produces a matching temp. The temp is still created beside FILE, readable by its owner only, and removed on any error; the published file is unchanged. A `FILE.partial` left by an older version, a `.FILE.<random>.partial` left by a killed backup and a `.ledger-backup.FILE.<random>.partial` left by a killed backup are all safe to delete when no backup is running. No schema or migration change.
- **`card` keeps `decided:` notes when it trims, and lists them under Decisions as notes.** An `item.note` whose text, after leading whitespace, starts with exactly `decided:` is dropped last, after every other note, and then oldest first if the card is still over the 400-word bound. The Decisions section lists each remaining one as a one-line note with its event id (`event=N note: ...`), never as an election: JSON marks it `as: note` and omits `quote_ref` and `chosen`, so a gate that counts `decision.elected` is unchanged. `Decided:`, `decided :` or a note that only contains the word elsewhere is still an ordinary note. A ruling on a busy parent item no longer vanishes with the bookkeeping. No schema or migration change.

- **A ledger open inside an exit handler is accepted; a ledger open outside the main interpreter is refused.** The connection capture the database file check installs with SQLite now stays registered until the process ends instead of being cancelled at exit, so the limit stated in 0.1.15 is gone: an exit handler registered before the process's first ledger open (exit handlers run last-registered first) now opens the ledger instead of being refused with `db_fd_unknown`, and a program whose first ledger open is inside an exit handler no longer crashes during interpreter shutdown. The capture's callback holds a reference that shutdown never releases and reads nothing from its module when SQLite calls it, so a connect during shutdown still reaches a live callback. Only the main interpreter installs the capture, from any of its threads: a ledger open in any other interpreter (a subinterpreter) is refused with `db_fd_unattributable` (`the capture hook installs only in the main interpreter, and this is another interpreter`) before anything is registered with SQLite, on every Python version; on 3.12 and later such an open was accepted before, and on 3.11 it was already refused, with another reason. When the interpreter cannot be told, the open is refused too. Known limit: once the main interpreter has installed the capture, a process that opens SQLite from an own-GIL subinterpreter on another thread can crash, because SQLite then runs the main interpreter's capture without that interpreter's GIL; that combination is unsupported, as it already was before this change. No schema or migration change.

Upgrade with `@v0.6.0`.

## 0.5.0 — 2026-11-19

An expired claim reads `open` in `query`, `ready` and `card`, `doctor` lists stale claims, refreshes the search index and prints the actor stamps a write would carry, every ledger open refuses a search index and the index writer never replaces a file that appears at its path, a refused write says its limit and the forms it allows, `resume --hook-env` and the plugin's hooks replace an inherited `cli` harness, and the install and upgrade pages are corrected.

- **The search index writer never replaces a file that appears at its path while it publishes, and the ledger refuses to open a search index.** `index`, `index --rebuild`, `search` and `doctor` build the index in a temporary file and used to rename it over `search.db` after checking that path, so a ledger created at `search.db` between the check and the rename was replaced, events and all. A path that was empty at the check is now published with a hard link, which never replaces a file; when the link finds one, the check runs again on what is there, and anything but a search index is refused with `refusing to replace PATH, which is not a search index, ...` (exit 3; `doctor` reports it as a warning). A path that is gone again by then is refused with `refusing to publish the search index at PATH: the path changed while it was published`, and a link that fails for any other reason is refused with `cannot publish the search index at PATH without replacing what may be there`; both exit 3 and leave the path as it was. Every ledger open (`--db` for any verb, and the library's `open_ledger`, `open_ledger_readonly` and `connect`) now refuses a file that has a search index's `manifest` table and no `events` table, with `refusing to open PATH as a ledger: it is a search index (a manifest table and no events table), not a ledger` (exit 3), before it migrates or writes anything. Before, `ledger --db DIR/search.db new` migrated the index and wrote an event into it, and the next index rebuild deleted that event while reporting success. The index writer and the open read one rule for what a search index is. Known limit: on a filesystem without hard links (exFAT, some SMB mounts) the first index build, where `search.db` does not exist yet, is refused, with no override; an existing index still updates. No schema or migration change.
- **`doctor` prints the actor stamps a write would carry.** It prints `actor`, `harness`, `model` and `session`, one `name: value` line each, and `--json` carries them as `stamps`; an unset or empty stamp is the word `missing`. The values come from the context every write is stamped from, so doctor shows what a write from the same environment records, and it reads no other environment variable. The agent contract's "Actor stamps" section names `ledger doctor` as the check to run before writing, for a machine whose guard denies `env` and `printenv`. In text a control character in a value prints as an escape. No schema or migration change.
- **Docs: the not-on-`PATH` upgrade route replaces the pipx command, and a hook comment names the empty-harness difference.** `docs/upgrading.md` 3.1 says outright that the venv-and-link route replaces the pipx install below it, so a reader does not end with both. The comment in `plugins/ledger-hooks/hooks/common.sh` says `resume --hook-env` matches the hooks for an unset and a `cli` harness, and differs for an empty one (the hooks pass `claude-code`; `--hook-env` keeps the empty value and prints no line). No behaviour change.
- **A `too-long` refusal carries the limit and the length given; a bad ref names the allowed forms.** The refusal keeps its reason and path first, so a caller that matches `too-long:point` or `bad-type:refs[0]` still matches: `too-long:point; max 600, got 643`, `too-long:refs; max 20, got 21`, and for a ref that is not a file path, a pull request or issue (`#12` or `owner/repo#12`), `branch:NAME`, a commit sha of 7 to 40 lowercase hex digits or `event:N`, `bad-type:refs[0]; allowed: ...` followed by the forms with an example each and the route for a URL: `ledger link ITEM --rel url --target URL`. A URL is still refused as a ref. The agent contract page and `resume --brief` now state the `point` limit, the ref forms and the item types `new --type` takes (`topic`, `ticket`, `initiative`, `decision`, `gate`, `guidance`). No schema or migration change.
- **`resume --hook-env` prints `LEDGER_HARNESS=claude-code` when the inherited value is unset or exactly `cli`.** Before, only an unset value got the line, so a session started from a shell whose profile exports `LEDGER_HARNESS=cli` stamped every write `cli`. Any other value, an empty one included, is kept. The plugin's hooks apply the same rule to the harness their own writes carry, and also treat an empty value as unset (`claude-code`); a plugin installed from a pinned marketplace must be re-pinned to get it. The install pages now put `LEDGER_HARNESS=claude-code` in the `env` block of Claude Code's settings and keep `cli` in the shell profile, and the `unset LEDGER_HARNESS` instruction is gone: measured with Claude Code 2.1.328, a session launched from a shell that exported `LEDGER_HARNESS=cli`, with `claude-code` in its settings `env` block, saw `claude-code` from its Bash tool.
- **Docs: an upgrade route for a ledger that is not on `PATH`, `claim-system` on a repeat run, and the settings file order.** `docs/upgrading.md` 3.1 gains the route for a vendored or wrapped copy (a virtual environment on a Python that passes the 1.1 probe, the tag installed into it, a link onto `PATH`, and every caller of the old copy listed before the new one writes, because the old copy cannot open a database the new one has migrated); section 3 says `claude plugin install` rewrites `~/.claude/settings.json`, so install the plugins before editing it or re-read it first. `docs/start-here.md` step 7, the README verb table, `docs/cli.md` and the `claim-system` help text no longer say a repeat run "changes nothing": it writes no event, but it opens the database for writing and applies pending migrations, after which an older copy refuses the file.
- **An expired claim reads `open` in `query`, `ready` and `card`; `doctor` lists stale claims and refreshes the search index.** A claim whose lease has expired now shows `open` (before, `ready` listed it as `claimed`); `--json` keeps `recorded_status` (`claimed`), `expired_holder` and `expires_at`, and `query --status` filters on the status shown. The ledger still records the claim: guards and write verbs read the recorded status, `claim` takes it over and records `prior_holder`, and no read writes an event. A claim with no lease stamp never reads `open`; once its claim event is older than 7 days `doctor` lists it under `stale_claims` (text: `stale claim:`) with a release command naming the database and `--expect-revision`, which doctor prints and never runs, and `query` rows carry `stale_claim` and `claim_age_seconds`. `doctor` brings the search index up to date before it reports it, so after a write it reports `current`; where it cannot write the index it reports the state it reads with the same exit code and JSON shape. No schema or migration change.

## 0.4.0 — 2026-11-16

Item text is printed with its control characters escaped and new text holding them is refused, `backup --to` refuses an existing destination, `spec show` and `spec diff` run without `LEDGER_HARNESS`, `link --rel pr` checks its target, and the `ledger-hooks` plugin ships its own `ledger` command and takes plugin options.

- **Item text is printed with its control characters escaped, and new item text holding them is refused.** `ledger card` (and its `--md` file), `spec show`, `spec diff`, `export-item`, `context`, `search` and the item listings of `query` and `ready` printed stored text as it was stored, so a note holding ESC `]52;...` BEL could write the operator's clipboard and ESC `[2J` could clear the screen. Each now prints every control character, the Unicode line and paragraph separators (U+2028, U+2029) and the bidirectional controls (U+202A to U+202E, U+2066 to U+2069) as a visible escape such as `\u001b`. One-line fields (titles, ids, names, card rows) also print LF, CR and TAB as `\n`, `\r` and `\t`, so a multi-line note now prints on one card line; a spec body, its acceptance and an `export-item --ticket` section keep their lines and tabs. `--json` output keeps the stored text, which JSON already escapes. At write time, `item.note` and `item.progress` text and an `item.spec` body and acceptance holding any of those code points other than LF and TAB are refused, and so is an item title or spec title holding any of them, LF and TAB included; the refusal is `display_control_character:<kind>.<field>` (exit 3) and nothing is written. Rows written before this release still verify, export, restore and print, escaped. Known limit: CR is refused everywhere, so a `spec set --body-file` with Windows (CRLF) line endings is refused, with a message that says to convert line endings to LF; the file is now read without newline translation so the CR reaches the check. A command the card prints (its recovery commands, footer and next step) spells an id holding such a code point as `"$(printf '%b' '...')"`, with no raw control and no bare quote, which bash, zsh, sh and dash all decode back to the stored id. Known limit: an id that ends in a line feed loses it in that command, because command substitution drops trailing newlines.

## 0.3.0 — 2026-11-15

A write is reported only once the database path still names the file it was written to; `backup` and `restore` tell a destination from the live database by file identity, not by spelling; two simultaneous first claims of the same name both succeed; the plugin's model stamp follows a mid-session model switch, and a keyed retry after a switch is no longer refused; prompt capture and picker capture can skip an opted-out folder; `resume --brief` prints the ledger version first; and library callers get the proof from `checked_connect` and `connect`.

- **A write is checked against its open before it is reported.** The open check already proved that the connection's descriptors are the files at the database's names; it now keeps that proof. After each write is durable (after its `COMMIT`, and for `claim-system` after the checkpoint that settles the claim), and after `open_ledger` migrates, the ledger checks the main file, `-wal`, `-shm` and the main file again: each name must still be a regular, singly linked file that is the proved one, and the connection must still hold the proved descriptor. If another file was put at one of those names, for example by a `backup --to` aimed at the live database's path, the write is refused with `db_swapped` or `db_sibling_unsafe` (exit 3) instead of reporting success. The write did land. When the main file was swapped, it is in a file the path no longer names, so it is not in the database at that path. When only the `-wal` or `-shm` name was swapped, the refused connection's close checkpoint writes the write into the main file, which still names the proved database, so it is in the database at that path; the ledger does not retry or roll it back either way. Each database-writing verb, `doc add` included, checks after its own commit. `restore` checks after the commit of its replay, so a restore of an export that already carries a system claim is checked too, and after its later writes (the claim of an unclaimed export, the receipt of a loop-managed export). The guard accepts nothing it refused before.
- **A refused write leaves the `-wal` and `-shm` names alone.** When the check refuses, the connection is set to keep both names when it closes (SQLite's `SQLITE_FCNTL_PERSIST_WAL`). SQLite's close otherwise unlinks both names, whatever files they hold by then, so a refusal caused by another file at one of them, such as a backup published there, would go on to delete that file. This holds for the ledger's own connection, `restore`'s and `backup`'s source connection. A file left on a `-wal` or `-shm` name survives the refused close only until the ledger next opens that database: the next last close of an ordinary connection removes it. A file moved onto a live `-wal` or `-shm` name by anything other than a ledger verb is still removed by a later last closer that is not the refused connection (see KNOWN-LIMITS.md).
- **A refused restore unlinks nothing.** When a restore is refused with one of those codes for the destination or its `-wal` or `-shm` name, the files at those names are no longer the ones it wrote, so it leaves them in place and names them in the refusal. Any other restore failure, including one of those codes about another path, removes the restore's own files as before.
- **`backup` and `restore` refuse a destination named like a database side file.** A destination whose name ends in `-wal`, `-shm` or `-journal` is refused by name alone, before anything is written, because SQLite removes a file on those names when the last connection to a database closes. `backup` keeps its earlier refusal of its own source's side names first, with its own message.
- **`backup` and `restore` tell a destination from the live database by file identity, not by spelling.** macOS's default volume ignores case and Unicode normalization, so a destination spelled `LEDGER.db`, or with a decomposed accented letter where the live database's name has a composed one, can be the live file; comparing names missed the second, and `backup` published its copy over the live database, losing the events committed while it ran. A hard link is another name for the same file on any volume. `backup` now refuses a destination that exists and is the live database, its `-wal`, `-shm` or `-journal` file (same device and inode, read without following a symbolic link), and still refuses its source's exact side-file names; it runs this check before anything else reads the source. `restore` refuses a destination any file already has, by the same identity read. A destination whose identity cannot be read is refused (`backup target cannot be told apart from the live database`, `restore target cannot be checked`), never published over. The side-file name refusal ignores case only where the destination's folder folds case: on a volume that tells case apart, `copy.db-WAL` and a real sibling `LEDGER.db` are ordinary destinations. The folder is probed by looking up one of its own entries with the case swapped; an empty folder, or one whose entries hold no ASCII letter, is treated as folding, so such a name is still refused there.
- **`backup` writes its copy at a unique name and checks its source before publishing.** The copy is written at `.FILE.<random>.partial` beside FILE, created readable by its owner only, instead of the fixed `FILE.partial`, so two backups to the same FILE no longer delete each other's copy; the published file keeps those owner-only permissions. Before the copy is renamed into place, the source path must still name the file it was read from (`db_swapped` otherwise), and nothing is published. A `FILE.partial` left by an older version is no longer removed by the next backup. A backup killed mid-run (by a signal or a power loss) leaves its hidden `.FILE.<random>.partial` behind, and no later backup removes it.
- **Two simultaneous first claims of the same name both succeed.** Two `claim-system NAME` callers on a new database each checkpoint the database after their commit, and one checkpoint could find the other's still running; that caller was refused `shared_database` (exit 3) although the claim was recorded. The verb now reads the claim back on the connection it opened and retries the checkpoint, up to 5 attempts started within 1 second, after a checkpoint that cannot finish or an I/O error in the claim's transaction. It exits 0 only when the name's claim is on record, a checkpoint finishes and the database path still names the files it opened (the same open check every write uses); `claimed` is `true` only when this call's write is known to have committed the claim, so exactly one of two simultaneous callers says `claimed`. A claim on record whose checkpoint is still held when the budget is spent, a read-back or checkpoint that fails, or a name not on record is still refused `shared_database`, and a swapped path `db_swapped` or `db_sibling_unsafe`. The library call `claim_database` settles the same way, on the database it opened, and returns only on that proof; `restore` is unchanged: it still raises on the first checkpoint that cannot finish. Library: `Ledger.claim_system` raises `UnsettledClaimError`, a `SharedDatabaseError`, for those two failures, and `Ledger.claim_outcome(system, refusal)` settles it or raises it again.
- **A keyed retry after a model switch is no longer refused.** A write retried with the same `--idempotency-key` and the same content was refused `conflict` (exit 3) when `LEDGER_MODEL` had changed since the first call, although the retry rule promises the first event back. The model is attribution, not content, so it is no longer compared: the retry exits 0 with the first event's id, writes nothing, and the stored event keeps the first model. A different actor, harness, session, channel or provenance class, or different content, is still refused `conflict` as before. The library's `Ledger.append` follows the same rule.
- **Library: `checked_connect` and `connect` return the proof.** `ledger.dbfile.checked_connect` returns `(conn, mode, proof)`, `ledger.store.connect` returns `(conn, proof)`, and `Ledger(conn, path, proof)` takes the proof; `ledger.dbfile.verify_bound(proof)` runs the check. A caller that unpacked two values from `checked_connect`, or used `connect`'s return as a connection, must unpack the new shape. `open_ledger` and `open_ledger_readonly` are unchanged for callers.
- **Prompt capture can skip a folder's sessions and injected prompts.** Two new keys in `config.json` beside the database. `capture_optout_paths` is an array of absolute paths: a prompt whose hook `cwd` is one of them or lies under one writes nothing and prints `skipped<TAB>cwd_optout`. The comparison resolves symbolic links and `..` on both sides and ends at a path separator, so a link into an opted-out folder opts out and a sibling such as `<folder>foo` is still captured; `~` is never expanded. Where the filesystem treats names that differ only in letter case or Unicode form as one name (the macOS default), an opted-out folder that exists is also matched by file identity (device and inode), so those spellings opt out too; an opted-out path that does not exist yet is matched by its text alone, letter case and Unicode form exact. If an opted-out path is configured and the ledger cannot decide whether the `cwd` is that folder (a `stat` fails for a reason other than the path not existing, on an opted-out path or, when one exists, on the `cwd` or a folder above it), the prompt writes nothing and prints `skipped<TAB>cwd_unverified`: the opt-out fails closed. A value that is not an array of absolute path strings refuses prompt capture with `capture_config` (exit 3) and writes nothing, and with a path configured a hook `cwd` that is not an absolute path is refused `capture_bad_input`. `capture_skip_prefixes` is an array of non-empty strings: a prompt that starts with one, after leading ASCII whitespace, writes nothing and prints `skipped<TAB>injected`. A valid array replaces the built-in list, which is empty; an absent key or an invalid value keeps the built-in list and capture goes on. The harness frames stay fixed. The checks run in the order frame, injected, cwd opt-out, `capture_prompts`, all before the database is opened, and `config.json` is now read once per prompt. The `ledger-hooks` plugin is unchanged: its prompt hook already passes the hook input, `cwd` included, to the CLI. Picker capture never reads `capture_skip_prefixes`.
- **Picker capture honours the cwd opt-out.** `ledger capture --kind picker` now applies `capture_optout_paths` as prompt capture does, by the same rule: a picker answer whose hook `cwd` is one of the paths or lies under one, through a symbolic link, a `..` path, or a spelling that differs only in letter case or Unicode form where the filesystem treats it as the same folder, writes nothing and prints `skipped<TAB>cwd_optout`; when the folder's identity cannot be read it prints `skipped<TAB>cwd_unverified`, and a sibling such as `<folder>foo` is still captured. The picker input is checked first, so every picker refusal still applies, and both skips happen before the database is opened, so neither creates it. An invalid `capture_optout_paths`, or a `config.json` that cannot be read or is not a JSON object, now refuses picker capture with `capture_config` (exit 3) and writes nothing, where before picker capture ignored the config; with a path configured, a hook `cwd` that is not an absolute path is refused `capture_bad_input`. `capture_prompts` and `capture_skip_prefixes` still never apply to a picker answer. The `ledger-hooks` plugin is unchanged: its picker hook already passes the hook input, `cwd` included, to the CLI.
- **The model stamp follows a model switch.** A session the `ledger-hooks` plugin started recorded no model on its writes, because only a few hook events may write Claude Code's environment file and a model switch is not one of them. The plugin now records the session's model in one small file per session beside the database (`<database>.session-models/`): the SessionStart hook records the start model and a new PostModelSwitch hook records each switch, through the new `ledger resume --hook-model`. Every write stamps its own session's recorded model, else `LEDGER_MODEL`, else none, so writes before a switch carry the old model and writes after it the new one; a record for another session or another database is never read, and an unusable record falls back to `LEDGER_MODEL` without failing the write. A switch to a model the hook cannot name records that the model is unknown, so writes stamp none rather than an older model. The session file wins over an exported `LEDGER_MODEL`. `--hook-env` still prints no `LEDGER_MODEL` line. A failed record is one line the person sees (`ledger-hooks: model record failed (exit N)`); Claude does not see it. Limits, including a prompt captured right after a switch, are in KNOWN-LIMITS.md.
- **`resume --brief` prints the ledger version first.** The first line of its text output is now exactly what `ledger --version` prints (`ledger X.Y.Z`), then the short form of the agent contract and the stops, so a session-start hook that prints the brief also shows which ledger is running. With `--json`, `--brief` adds `version` (the bare version number, such as `0.3.0`) beside `contract`. It prints the line even when no database exists yet. `resume` without `--brief` is unchanged. Anything that matches the brief's output from its first character needs updating; the brief gains one line at the top.

**Upgrading from 0.2.1.** There is no schema change and no migration. The plugin's PostModelSwitch hook needs Claude Code v2.1.251 or later. Picker capture now refuses with `capture_config` (exit 3) and writes nothing when `config.json` beside the database cannot be read or is not a JSON object, or when `capture_optout_paths` is invalid; before, it ignored the config. Library callers must unpack the proof: `ledger.dbfile.checked_connect` returns `(conn, mode, proof)` and `ledger.store.connect` returns `(conn, proof)`. A backup destination may hold a `FILE.partial` from an older version, or a `.FILE.<random>.partial` from a killed backup; either is safe to delete when no backup is running.

## 0.2.1 — 2026-11-13

Two fixes to `ledger export --commit` and `--push`: committing no longer throws away what you staged in the export repository, and the credential scan now covers the text of every event, not only attached documents.

- **`export --commit` keeps what you staged in the export repository.** 0.2.0 set the repository's index to the new commit's tree after every commit, which silently dropped anything you had staged there (a staged edit came back as the committed content, and the repository looked clean). The commit step now merges the index from the old head onto the new commit, as `git read-tree -m -i` does: paths the export changed take the new content, and every staged change, staged deletion and staged new file stays staged with the same content. When something staged sits on a path the commit also changed, the index is left exactly as it was and `index_refreshed` is false; the warning now points at `git status` rather than a command that would drop staged changes. `export --push` never touches the index.
- **The export credential scan covers every event's text.** 0.2.0 scanned only `doc.attached` documents, so a credential pasted into a note, an item or spec title, a spec body, a claim owner or any other text field passed `export`, `export --commit` and `export --push` and could reach the remote. Every event kind is now scanned: every text field and key the event file holds, plus a document's bytes or stored path. A hit refuses with the existing `export_doc_credential` (exit 3), naming the event, its item, the field and the shapes, never the text; nothing is written, committed or pushed. Text the scan cannot read (not UTF-8) is refused the same way. `credential_override: true` still lets an attached document through, and only that: it changes nothing on any other event. The ledger never removes an event, so a refused event keeps refusing later exports, and an export repository whose history already holds such an event file refuses `--push` until that file is removed from its history with git (rotate the credential if it was pushed before).

**Upgrading from 0.2.0.** There is no schema change and no migration. If you run a scheduled export, run `ledger export --dir DIR --commit` and then `--push` once by hand after upgrading, before the next scheduled run: an event already in the ledger, or already committed in the export repository, whose text holds a credential shape is now refused by name where 0.2.0 exported and pushed it.

- **A `child-of` link must name an item that exists.** The store now refuses a `child-of` event whose target is not an item, for `append`, `append-many` and `restore` as well as `link` (exit 3, code `anchor_missing`; a refused `append-many` batch writes nothing). Before, such a link was accepted and `parent_id` held the missing id for good. An anchor created earlier in the same batch or restore counts. An export that already holds a `child-of` link to a missing anchor, or a link that comes before its anchor's creation, now fails `restore` with `anchor_missing`.
- **`link --rel child-of` with an `--idempotency-key` is refused (code `key_on_noop`) when the child already has that anchor.** The call writes no event, so the key named nothing, and after the child later moved the same retry failed as `second_anchor`. Without a key the call still writes nothing and reports `unchanged`. A keyed call that wrote an event replays as before.
- **The Children section of an anchor's card keeps each child on one line.** A newline, carriage return, tab or other control character in a child's title or holder is shown as a visible escape (for example `\n`), so a title can no longer start a heading inside the card. `card --json` still carries the raw strings.

Upgrade with `@v0.1.12`.

## 0.1.11 — 2026-11-07

- **`ledger spec set` records a source-only change.** The same content with a different `--source` now writes the next spec version, carrying the same content and the new source, and the item's current spec source becomes the new one. The same content with the same source still writes nothing and reports `unchanged`, and so does a call with no `--source`. Moving the source back to an earlier value is another change. `--source-rev` still does not version the spec. Before, only a content change wrote a version, so a caller that moved the source alone could not record it. A claimant's card and `pick` print `spec moved: vN → vM` only when the content hash of the current spec differs from that of the version the claim stamped, so a source-only move does not report one; when the claimed version's event cannot be found, the version numbers decide as before.

Upgrade with `@v0.1.11`.

## 0.1.9 — 2026-11-07

Anchors and children. Nothing is renamed, and every command that worked in 0.1.8 works the same way. There is one schema migration (version 10) that replaces a view and leaves every event as it was.

- **`ledger link CHILD --rel child-of ANCHOR`** makes an item a child of an anchor. An anchor is an item that groups others; a child has one current anchor at a time. A second anchor is refused (exit 3, naming the current one) unless `--move` is passed, and a move appends a new link that names the anchor it left; earlier events never change. Linking again to the same anchor writes nothing. A link that would make an item its own ancestor, including a link to itself, is refused and writes nothing. `--move` is accepted only with `--rel child-of`. The store holds the same rules for every writer: a `child-of` event written with `append` or `append-many`, or replayed by `restore`, is refused the same way (a second anchor needs `moved_from` naming the current one), and a refused `append-many` batch writes nothing.
- **The anchor's card has a Children section** with one line per child (id, title, status, holder), a child that `blocks` another first and creation order otherwise, under a `closed/total` count. An item with no children shows no section. `card --json` carries the same rows and the count, and `resume` prints the count for an anchor. When a long card cuts the section, its marker names `ledger query --parent=ANCHOR --all`, which lists every child the anchor has when the command runs.
- **`ledger query --parent ID`** lists the children of `ID`. **`ledger query --all`** removes the row cap; it cannot be combined with `--limit`.
- **A retry of `link --rel child-of` under the same idempotency key from a different session or actor is now refused as `conflict` (exit 3),** as on every other relation. Before, it returned the stored event.
- **`v_items` gains two columns,** after `spec_version`: `parent_id` (the item's current anchor, or NULL) and `children_open` (how many of its children are not closed). The migration is `0010_child_of.sql`.

Upgrade with `@v0.1.9`.

## 0.1.8 — 2026-11-06

Three read-only commands for looking at a store. Nothing is renamed, there is no schema change, and every command that worked in 0.1.7 works the same way.

- **`ledger events`** lists events across all items, newest first. `--since` / `--until` use the same date grammar as `query`; `--kind` is repeatable; `--item`, `--actor` and `--limit` narrow the list. Filters combine with AND.
- **`doctor --json`** adds a `summary` object: counts of items by type and status, the event log's size and newest timestamp, open questions, claimed items, including expired ones (which `expired_claims` lists), and (when `LEDGER_EXPORT_DIR` is set) how far the export watermark is behind. A read failure on the summary or the watermark marks that part `unknown` and never changes doctor's exit code. There is no `last_export_at` because the watermark sidecar records only an event id, and no `verify` field because verify runs are not recorded anywhere.

## 0.1.6 — 2026-11-05

`ledger link --rel duplicate-of --idempotency-key K` now reserves `K` itself. Before, it wrote its two events under `K:link` and `K:close` and never looked at `K`, so a plain `link` under `K` followed by a `duplicate-of` call under the same `K` succeeded, wrote both events and closed the item. Now the link event of a duplicate-of is written under `K` (the same slot a plain link uses) and the close under `K:close`. The same key with another mode, target or content is refused as `conflict` (exit 3) and writes nothing; a retry of the same call still returns both stored events; only one of the pair present still refuses as `partial_write`. A duplicate-of written under 0.1.5 stored its link as `K:link`, which this version does not read as `K`; retry such a call across the upgrade with a new key (LC34).

Upgrade with `@v0.1.6`.

## 0.1.5 — 2026-11-05

Two fixes for everyday agent use. Nothing is renamed, and every command that worked in 0.1.4 works the same way.

- **A write no longer makes the search index read "stale".** After a rebuild, any ordinary write (a note, or a session's `item.stopped`) used to turn `doctor` to `search: stale`, though search kept working. The index now has a `behind` state: it is a clean prefix of the event log and newer events exist. `doctor` prints `search: current to event N, M new event(s) will be indexed on the next search`, and its JSON status is `behind`. `stale` now means a real mismatch: a changed format, ranker, database or roots; an added, edited or deleted source file; or an event log that no longer matches the record. Search still rebuilds before answering whenever the index isn't `current`, so it never answers from an index that is missing events (LC27).
- **`note`, `link` and `elect` take `--idempotency-key`,** with the same retry rule as `append` and `pick`. The same key with the same content returns the stored event and writes nothing. The same key with different content is refused as `conflict` (exit 3). Before this, these three verbs always minted a fresh key, so an agent that retried one after a timeout wrote the event twice. `link --rel duplicate-of` covers both of its events with one key, and refuses as `partial_write` if only one of them is present. See "Retrying with a key" in `docs/cli.md` (LC28).

Upgrade with `@v0.1.5`.

## 0.1.1 — 2026-11-05

This release is for the agent using the ledger, not only the person who installed it.
Nothing is renamed and every command that worked in 0.1.0 still works the same way.

### New: `ledger resume`

- `ledger resume` lists every open item that has a stop stamp: where it stopped, the
  phase, the skills to run next, the files to read, and the exact commands to continue.
- `ledger resume --item <id>` shows one item.
- `ledger resume --brief` prints a short form of the agent contract first, then the
  list. This is what the sdlc plugin's session-start hook prints (plugin 0.11.0), so
  every session starts knowing the ledger exists, what to write without asking, and
  where the last session stopped. It only reads; with no database yet it prints
  `no open items`.
- The full agent-facing page is `docs/agent-contract.md`: when to write, the reading
  order (`resume`, `card`, then `export-item` when the card shows a cut), what each
  `LEDGER_*` stamp is for, and the close rule (write `item.stopped`, then print the
  resume command).
- The card's default next step now reads `Resume with: ledger resume --item <id>`.

### Verbs work on the first try

- `ledger note <item> "text"` works (as well as `--text`).
- `ledger link <item> <target>` works, with `--rel` defaulting to `url`; a local file
  path is a fine target.
- `ledger search several words` works without quotes.
- `note`, `link` and `elect` `--help` end with worked examples. `elect --help` says
  `--rejected` is required and repeatable.
- `ledger query --since/--until` filters items by date, with the same date forms as
  `search`.

### Knowing you have the whole record

- `ledger export-item` ends with one line: events returned, events on the item, and
  events decayed (`--json` carries the same numbers as `data.completeness`).
- Every `(+K cut)` marker on a card names the command that recovers it, and the footer
  says the events are the authority.
- `search` refuses by name, instead of crashing, when it cannot rebuild a stale index.

### Upgrading

Install the tag into the environment you already use, for example:

    ~/.local/share/ledger/venv/bin/pip install "git+https://github.com/smithadifd/ledger.git@v0.1.1"

Then check it with `ledger resume --brief`: it should print the short contract. No
database migration is needed.

For session ids on every event, let the sdlc plugin 0.11.0 hook set `LEDGER_SESSION`,
and set `LEDGER_AGENT` yourself if you want a name other than `claude-code`.
